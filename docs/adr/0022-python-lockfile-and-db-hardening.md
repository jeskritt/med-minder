# ADR-0022 — Python 3.14, locked backend dependencies, two-role DB, and TLS verification

## Status

**Accepted** (post-Phase 10 security hardening). Supplements
[ADR-0017](0017-single-service-deployment.md).

## Context

After deploying MedMinder to Render + Supabase, three supply-chain and database
hardening gaps remained open:

1. **Floating backend dependencies & Python version drift.** Production and dev
   Dockerfiles ran `pip install .` / `pip install -e ".[dev]"` against loose
   version ranges on Python 3.12, while developer workstations ran Python 3.14.
   A fresh deploy or CI run could silently pull a newly published transitive
   package version that had not been audited or tested locally.
2. **Single privileged database role.** The production container ran
   `alembic upgrade head` on startup using `DATABASE_URL`, coupling the runtime
   FastAPI app to a DDL-capable Postgres role. The project constitution
   requires separating the DDL migration role from a DML-only runtime role.
3. **Opportunistic DB TLS (`ssl=prefer`).** Neither `asyncpg` nor `psycopg`
   enforced certificate/hostname verification against Supabase, leaving
   connections theoretically vulnerable to TLS downgrade or MITM. Additionally,
   Render Secret Files mounted at `/etc/secrets/*` require container group
   `1000` for non-root Docker users to read them.

## Decision

### 1. Standardise on Python 3.14 and lock dependencies with `uv.lock`

- Upgrade `requires-python`, Ruff `target-version`, both Dockerfiles, and CI
  from Python 3.12 to **Python 3.14** (active bugfix until Oct 2027, EOL Oct
  2030, mature binary wheels across our dependency graph, matching local dev).
  Python 3.15 (released Oct 2026) is deferred until binary wheel coverage
  across all dependencies stabilises.
- Commit a universal cross-platform `backend/uv.lock` generated by `uv lock`.
- Pin `uv` in `Dockerfile`, `backend/Dockerfile`, and `.github/workflows/ci.yml`
  and install strictly via `uv sync --frozen` (production uses `--no-dev
  --no-editable`).
- In CI's `security-audit` job, export the locked graph via
  `uv export --frozen --extra dev --no-emit-project --no-hashes` and run
  `uvx pip-audit -r ... --no-deps --disable-pip` so the audit checks the exact
  locked versions without mixing in `pip-audit`'s own transitive dependencies.

### 2. Support two Postgres roles and out-of-band migrations

- Add optional `MIGRATION_DATABASE_URL` to `Settings`. `Settings.database_url_sync`
  (used by `alembic/env.py`) and `medminder-admin db backup|restore` prefer
  `MIGRATION_DATABASE_URL` when set and fall back to `DATABASE_URL` when unset
  (preserving zero-config local dev, CI, and existing deploys).
- Add `RUN_MIGRATIONS_ON_STARTUP` (default `true`) to the production
  `Dockerfile` entrypoint. Setting `RUN_MIGRATIONS_ON_STARTUP=false` on Render
  skips startup migrations so the runtime container only holds the DML-only
  `DATABASE_URL` and **never** has DDL credentials in its environment; schema
  migrations are run out-of-band from a workstation or CI job before deploy
  (documented in `docs/operations.md`).

### 3. Enforce PostgreSQL TLS verification uniformly across drivers

- Add optional `DATABASE_SSL_MODE` (`disable`, `allow`, `prefer`, `require`,
  `verify-ca`, `verify-full`) and `DATABASE_SSL_CA_FILE` to `Settings`. Setting
  `DATABASE_SSL_CA_FILE` without `verify-ca` or `verify-full` raises a startup
  validation error to prevent silent misconfiguration.
- Wire both settings uniformly into:
  - `medminder.db.make_async_engine` (`asyncpg` receives an explicit
    `ssl.SSLContext` with `CERT_REQUIRED` and `check_hostname` for
    `verify-ca`/`verify-full`),
  - `backend/alembic/env.py` (`psycopg` receives `sslmode` and `sslrootcert`),
  - `medminder.cli.db` (`pg_dump`/`pg_restore` receive `PGSSLMODE` and
    `PGSSLROOTCERT`).
- Run the production container's non-root `appuser` with UID/GID `1000` so
  Render Secret Files (e.g. `/etc/secrets/supabase-ca.crt`) are readable
  without running as `root`.

## Consequences

### Positive

- Production, dev, and CI builds are reproducible and audited against the exact
  same locked Python 3.14 dependency graph.
- Production deployments on Render Free can eliminate DDL credentials from the
  runtime container entirely while keeping zero-config defaults for local dev.
- PostgreSQL connections can enforce full CA + hostname TLS verification
  (`verify-full`) across runtime queries, migrations, and backups with a single
  pair of environment variables.

### Negative

- Updating a Python dependency now requires running `uv lock` (or
  `uv lock --upgrade`) and committing `backend/uv.lock`.
- When `RUN_MIGRATIONS_ON_STARTUP=false` is enabled in production, any deploy
  that introduces a new Alembic revision requires running `alembic upgrade head`
  before (or immediately alongside) the Render deploy.

### Neutral

- Local Docker Compose and CI continue to use a single `DATABASE_URL` without
  TLS overrides; existing Render deployments keep working unchanged until the
  operator opts into the two-role and `verify-full` cutover described in
  `docs/operations.md`.
