# Phase 1 Data Model — Phase 8 (PWA Polish)

**No database schema change.** Phase 8 adds **no tables, columns, indexes, or migration**.
This document records (a) the entities the one new endpoint reads/writes, (b) the
notification-action data flow, and (c) the client-side cache "data model" — what the service
worker is allowed to store, which is the security-relevant part.

## Existing entities reused (unchanged)

- **Reminder** (`reminders`) — the take action targets a **dose** reminder by id. Read:
  `id`, `user_id` (ownership), `type` (must be `dose`), `schedule_id` (the slot), `status`.
  Written: the slot's open reminder(s) become `dismissed` via the existing
  `resolve_dose_reminders`. No new columns; the lifecycle is unchanged from Phase 7
  (`pending → sent`, with `snoozed`/`dismissed` terminal).
- **Schedule / ScheduleMedication** (`schedules`, `schedule_medications`) — to resolve "which
  medications are in this slot," the endpoint joins `ScheduleMedication` → `Schedule` filtering
  `Schedule.deleted_at IS NULL` (and excludes soft-deleted meds), the same pattern
  `domain/doses.py` already uses. Read-only here.
- **Dose** (`doses`) — append-only; the take action inserts **one row per attached medication**
  via the existing `create_dose` (which also decrements `medications.refill_count` and may raise
  the Phase 5/6 guards). No change to the `doses` shape.
- **Medication** (`medications`) — read for the slot's meds and their guard inputs
  (`timer_preference`, `min_interval_minutes`, `times_per_day`, `window_duration_minutes`,
  `max_doses_per_day`, interaction rules); `refill_count` is decremented by `create_dose` as
  usual. No change.
- **PushSubscription** (`push_subscriptions`) — unchanged; enablement still
  creates/removes it through the existing Phase 7 endpoints. Phase 8 only polishes the client
  UX around it.
- **User** (`users`) — ownership scoping for the reminder/dose; `timezone` already used by
  `resolve_dose_reminders` for the "today" window. No change.

## New endpoint data flow — `POST /api/v1/reminders/{reminder_id}/take`

Server-authoritative, **atomic** (single request transaction):

1. **Load** the reminder; reject if not owned by the caller (`_load_owned_reminder` → 404) or
   not a `dose` reminder with a `schedule_id` (→ 409/422; take is dose-only).
2. **Resolve** the slot's medications: non-deleted meds linked to `reminder.schedule_id`.
   Empty set → idempotent **204** (nothing to record; resolve any open reminder anyway).
3. **Record** a dose for **each** medication via `create_dose(user, medication_id,
   schedule_id=reminder.schedule_id, taken_at=now, interaction_acknowledged=False)`.
   - Any guard error from any med (`MinIntervalNotElapsedError`, `WindowFullError`,
     `DailyCapReachedError`, `MedicationInteractionConflictError`) → **roll back the whole
     transaction**, commit **nothing**, return **409** with the existing violation body.
4. **Resolve** the slot's open reminder(s): `resolve_dose_reminders(user,
   schedule_id=reminder.schedule_id, taken_at=now)` marks them `dismissed`.
5. **Commit** → **204**.

**Invariants**
- All-or-nothing: either every attached med's dose is recorded **and** the reminder is
  resolved, or **no** dose row is written and the reminder is untouched (FR-015).
- `interaction_acknowledged` is **never** set true from this path — an interaction cooldown is a
  hard 409 here; the informed override remains in-app only (FR-015/FR-016).
- Ownership: a reminder not belonging to the caller is indistinguishable from "not found"
  (404), matching snooze/dismiss (FR-016).

**State transition (the slot's dose reminder)**

```
pending ──take(success)──▶ dismissed
snoozed ──take(success)──▶ dismissed
pending ──take(guard 409)─▶ pending   (unchanged; nothing committed)
dismissed ─take(idempotent)▶ dismissed (204, no-op)
```

## Client-side cache "data model" (the security-relevant part)

The service worker's Cache Storage is constrained by policy (R2), not by a DB:

| Cache bucket | Contents | Notes |
|---|---|---|
| **Workbox precache** | Hashed static build assets (JS/CSS), icons, and the `index.html` shell | Versioned by the build; the offline navigation fallback serves the precached `index.html`. |
| **Runtime caches** | **None for `/api`** | `/api/*` is `NetworkOnly` — never written to any cache. No authenticated/medical response is persisted (FR-006/SC-004). |

**Asserted in tests**: `frontend/src/__tests__/sw-precache.test.ts` verifies the generated
precache manifest contains no `/api` entries and only static assets — the machine-checkable form
of "no PHI in caches."

## Manifest (not a DB entity)

The web app manifest (generated by `vite-plugin-pwa`) is a static build artifact:
`name=MedMinder`, `short_name=MedMinder`, `description`, `start_url=/`, `scope=/`,
`display=standalone`, `theme_color=#0f172a`, `background_color=#f8fafc`, and the icon set
(192/512 + maskable + apple-touch). It carries **no user data**.

## Summary

No migration, no `alembic check` impact, no ER diagram change. The one new endpoint is pure
read/insert/update over existing tables using existing domain functions; the only genuinely new
"model" is the **client cache policy**, whose single rule — *never cache `/api`* — is the
security crux of the phase.
